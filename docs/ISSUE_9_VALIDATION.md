# Issue #9：按设备能力和访问策略显示认证流程

## 判断依据

认证需求与保存状态分开计算。组合展示每个物理成员的名称、类型、在线状态、认证需求或已保存凭据；Apple TV 的要求不会传给 HomePod。较大组合仍使用既有主设备认证路径。

| 广播信息 | 认证需求与操作 |
| --- | --- |
| `acl=1` 或 `act=2` | 访问策略限制，检查家庭 App / 设备的 AirPlay 访问设置，保留已有凭据 |
| `pw=true` 或 `flags` / `sf` 的 `0x80` 位 | 设备密码，通过 `--password` 交给播放引擎，不走四位屏幕 PIN |
| `flags` / `sf` 的 `0x8` / `0x200` 位 | 屏幕 PIN 配对，有凭据时只在高级选项中提供重新配对 |
| 新鲜、可解析的状态与能力，具备引擎使用的 AirPlay 2 临时认证能力，且没有上述限制 | 无需额外配对（设备广播），可直接尝试播放 |
| 缺失、过期、冲突、无法解析的能力，或未知访问策略 | 明确标记未知，保留有说明的高级 PIN / 密码操作 |

开放访问判断与仓库固定版本 [cliairplay v0.5.3 的路由判断](https://github.com/music-assistant/airplay-cli/blob/v0.5.3/src/ap2_client.c) 一致：AirPlay 2 能力位 38 / 48，以及配对能力位 46 / 48。密码与家庭访问字段参考 [pyatv 的 AirPlay 服务发现](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/airplay/utils.py)。字段用于保守判断，不能保证某型号在所有固件和策略下均可直接播放。

引擎的 [`--password` 参数](https://github.com/music-assistant/airplay-cli/blob/v0.5.3/README.md) 用于 RAOP digest 或 AirPlay 2 临时认证。保存密码时合并该成员的原有记录，PIN 配对成功也保留原有密码。保存成功仅表示已持久化，下次连接才验证；失败、取消或页面刷新不清空旧凭据。密码不出现在状态、事件或错误详情中。

引擎结构化的 `auth_required` / `auth_failed` 错误映射为固定中文提示，不透传引擎详情。初始 HomePod 错误标注成员名称，Apple TV 加入时认证失败显示独立的降级原因，HomePod 继续播放。

## 自动化验证

- Go：认证能力/策略矩阵、缺失与损坏字段、过期广播、策略变化、成员隔离、凭据与密码保存/重启、PIN 配对兼容、密码子进程参数、认证错误脱敏、HTTP 认证与 CSRF。
- 前端：开放 HomePod 与需 PIN 的 Apple TV 分别展示、未知状态的高级入口、密码输入与错误提示、已保存状态、访问限制、离线 TV、独立 HomePod、PIN 弹窗标明成员并提交。
- 保留播放、组合加入、音量、账号与持久化的既有回归测试。

## 实机验证（待执行）

本地测试使用模拟引擎和发现记录，没有连接家庭设备。部署后按实际固件、设备访问设置和既有凭据进行验证：

1. 使用 issue 中已经可直接播放的 HomePod：页面不要求额外配对，选择组合仍可播放；若发现字段不足，显示未知并允许先播放。
2. 同组 Apple TV 未配对时，按该成员的屏幕 PIN 流程完成配对，HomePod 的状态与凭据不变化。
3. HomePod 开启设备密码后，等待新的发现记录；输入正确密码并重新连接，确认播放。使用错误密码，确认认证提示明确且不包含密码。
4. 开启仅限家庭成员等访问限制，确认页面提示检查访问设置，而非无效 PIN 流程。
5. 保留原 `state.json` 升级并重启，确认已有配对凭据继续使用；在电视离线、Apple TV 认证失败时，HomePod 仍按原有降级路径播放。
